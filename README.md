# interactive_plots

Interactive plots for Rubin Observatory data releases and documentation.

Each package here builds to plain JavaScript, CSS, and HTML, with no framework
required of whatever serves it, so the output can be dropped into a
documentation page, a static site, or any other web page.

## Packages

| Package                                 | Purpose                                                                                                     |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| [`dp2_data_quality`](dp2_data_quality/) | Sky maps of DP2 data quality metrics by tract and band, published on the Data quality page of dp2.lsst.io     |

Packages are independent: each has its own dependencies, build, data, and
`README.md`. That package README is authoritative for anything specific to it;
this file covers only what is common across them.

## Working on a package

Packages are standalone npm projects, driven from the package directory rather
than the repository root:

```bash
cd <package>
npm install
npm run dev        # dev server with hot reload
npm run build      # production bundle in dist/
```

A package whose plots read generated data fetches it separately, since the data
is regenerated by the pipelines that produce it and is too large to commit here:

```bash
make data          # rsync from the host where the data is produced
```

The source path is a Makefile variable so it can be pointed elsewhere; see the
package README for its default.

## Publishing into a documentation site

A package is published by building it and copying the result into the target
site, which commits it as a static artifact and never rebuilds it. `make deploy`
builds and installs in one step:

```bash
cd dp2_data_quality
make data                 # refresh the data first; the build bundles it
make deploy               # or: make deploy DEST=/path/to/site/_static/<package>
```

`DEST` defaults to a sibling checkout of the target site. The deploy installs
the bundle and its data, and writes a `PROVENANCE` file recording the commit it
was built from. Deploy from a clean tree: uncommitted changes add a `-dirty`
suffix, meaning the recorded commit alone will not reproduce the artifact.

### On the receiving site

How the artifact is committed is the site's business, but three things reliably
catch people out:

- **Rebuild with a clean.** Sphinx skips copying `_static` when no source page
  has changed, so an incremental build reports success while still serving the
  previous bundle. Use `make clean html`.
- **Exempt the artifact from formatters.** Generated bundles carry trailing
  whitespace and machine formatting that pre-commit and prettier will rewrite,
  and every redeploy puts it back.
- **Load the script from the page that uses it.** A stylesheet is small enough
  to attach site-wide, but the bundle is not, and Sphinx offers no per-page hook
  for scripts that does not also leak onto every page built afterwards.

## Writing a package that embeds cleanly

The host page owns the document. A package that assumes it owns the page will
break it. What works:

- **Resolve paths relative to the bundle** with `import.meta.url`, never from
  the site root. One bundle then works at a domain root and under a versioned
  preview prefix, with no configuration.
- **Scope every style to the mount point.** Rules on `:root`, `body`, or a bare
  `*` selector repaint the host page.
- **Inherit the host's colors** instead of declaring a palette. Reading the
  theme's CSS custom properties makes the plots follow its light and dark modes
  for free, and keeps them right when the theme is retinted.
- **Namespace class names.** Documentation themes often ship Bootstrap, whose
  `.modal`, `.btn`, and `.tooltip` rules will otherwise capture yours; a `.modal`
  that inherits `display: none` simply never appears.
- **Update the DOM in place rather than rebuilding it.** Themes commonly watch
  the article with a `MutationObserver`, so tearing down and recreating elements
  on every interaction costs far more inside a documentation page than it does
  standalone.
